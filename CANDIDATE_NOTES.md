# Candidate notes

## What I built and why

Task B, the monthly billing run. The role I'm applying for here is specifically 'backend leaning', so I ruled out A based on that being a clearly frontend-focused addition. Choosing between B and C was more interesting. In the end, I decided on B because I felt given the guidance on time that I would be able to show greater depth by focusing on the pure backend logic (though I did end up making a few small frontend tweaks) and my brain had already started a background thread on how this feature might look and scale over time.

All three billing endpoints are now implemented: `POST /api/billing/runs/`, `GET /api/invoices/?month=`, `GET /api/invoices/<id>/`. Each run creates invoices from approved hours (`TimesheetEntry` rows) and emails each invoice to the company's `billing_email` and to the freelancer. To both help with 'eyeballing' and validation, a small amount of frontend polish (invoice list columns, a proper invoice page, showing the API's validation message) was added alongside backend unit tests.

## Key implementation notes

- **Approach.** I settled the data model first and let it shape the endpoints. I also wanted to respect the 'spirit' of the assignment of this being a potential PR I would raise to an existing codebase, which shaped some choices on where things lived. Most notably, I would generally be reaching for a service-layer pattern here, but I noticed e.g. the contracts view had that kind of logic directly embedded in the view functions, so I copied that style. A bit of role playing, I suppose.
- **Data model.** `BillingRun` → `Invoice` (one per company × freelancer per run) → `InvoiceLine` (one per timesheet entry), plus `InvoiceEmail` (one per recipient). Invoices store `period_start`/`period_end` rather than a month as that struck me as an arbitrary (though sensible) choice of period and wanted to be somewhat forward-thinking. Lines copy the entry's date and hours and the contract's day rate at billing time, so any later edits don't change an issued invoice. The total is calculated as the sum of the lines, not stored, so that there is an undisputed source of truth for what the total is. Foreign keys right now use `PROTECT`, because invoices are financial records so how we deal with deletions generally needs proper product and regulatory thought (and not some engineering bozo like me pressing a big delete button in Django admin).
- **Billing rule.** The repo gives three different answers to how hours become money:
  - The README's domain: a contract has "a fixed daily rate", and freelancers log an entry "per day worked".
  - Task A's brief: "hours × contract rate". Taken literally with a daily rate, that bills an 8-hour day eight times over, so I suspect that's actually loose wording.
  - The `ContractDetail` page: an estimate of `hours × daily_rate / 8`, which pro-rates partial days.

  I followed the domain, based on my own personal experience with my freelance work (a flat day rate). Each approved entry bills one day at the contract's `daily_rate`, whatever its hours, so a 7.5-hour day (the seed data has these) costs a full day. Lines still copy the hours, so the invoice shows them. **This is the assumption I'd most want to confirm with product.** The total is the sum of each line's frozen rate, so issued invoices can't change. Switching to pro-rata would mean giving lines a stored amount, backfilled from `daily_rate` for existing invoices, so they keep their totals. Until it's confirmed, the `ContractDetail` estimate disagrees with invoices whenever a day isn't exactly 8 hours.
- **Idempotency.** `InvoiceLine` has a OneToOne link to `TimesheetEntry`, so the database guarantees no entry is billed twice. A re-run only bills entries that aren't on an invoice yet, so with nothing new it creates nothing, and a late `TimesheetEntry` approval goes on a supplementary invoice. This makes it safe to bill any month that has started, most obviously the current month part-way through. You shouldn't be able to invoice for work that can't have happened yet, so future months are rejected, and entries dated after today wait for a later run.
- **Transactions.** A run is one transaction. It locks the company row so two runs can't overlap, and it uses `bulk_create`, so the query count is fixed whatever the number of freelancers.
- **Email after commit.** Email rows are written as `pending` in the same transaction as the invoices, and only sent in `transaction.on_commit`. An SMTP failure after commit leaves the invoice in place, with the email marked `failed` and the error recorded. Re-running the month retries `pending`/`failed` emails, looking the address up again. Once `sent`, an email is never sent or re-addressed again. Delivery is at-least-once (a crash between the SMTP server accepting the message and the row being saved means a resend).
- **Access.** A new `IsCompanyAdmin` permission in `accounts`, given this is likely something that would be not specific to just billing. Another company's invoice returns 404 rather than 403, to help combat naughty people.
- **Testing.** Unit tests cover the edge cases (month boundaries, re-runs, rollback, email failures), and I checked them by deliberately breaking the code to make sure a test caught each break. I also ran the full flow locally against Mailpit. Concurrent runs aren't tested. I tried writing such a test twice at the same time, but the second attempt waited politely for the first.
- **Tooling.** Ruff and strict mypy apply only to new code, to keep the diff focused. I'd be a vocal advocate of getting that rolled out across-repo though.

## Workflow

I used Claude Code throughout, with ruff, strict mypy and pytest as guardrails. I settled the design first, then had it implement in small steps that I reviewed before moving on. I'm yet to find really good results letting the AI just run off on its own and am particularly annoying to it in that I am very insistent on understanding everything it is writing. I find that a useful workflow because it's then easier to spot little assumptions and implicit understanding before it's gone and built a tower on top of it. It occasionally stated things more confidently than it should have, so I questioned the choices that mattered, checked the tests by breaking the code, and ran the whole flow locally.

## Next steps (another four hours)

1. **Show email failures.** They're recorded but nothing displays them yet. For example, add an `emails_failed` count to the run response with a warning on the Billing page, and per-recipient email status on the invoice detail. Perhaps even a button/endpoint to retry emails for a given invoice, reusing the existing send path.
2. **Protect billed and approved data.** `PATCH /api/timesheets/<id>/` lets a freelancer approve their own entries, and lets anyone edit an entry after it's been billed. Restrict status changes to e.g. admins and lock billed entries. Also reject future-dated entries, which billing currently just defers.
3. **Make billing async.** `BillingRun` already has a status because it seemed clear to me that this will want to move out of the request cycle. The POST would return 202, a worker would generate invoices and send `pending` emails, and the frontend would e.g. poll.
4. **Smaller follow-ups.** Freelancers seeing their own invoices. Month boundaries in each company's time zone (it's always just using UTC today). Invoice numbering, currency, VAT, and copying company details onto the invoice.
